# SMTAP – Secure Multi-Tenant Audit Platform

> Enterprise-grade audit logging platform designed for secure event collection, multi-tenant isolation, tamper-evident storage, compliance reporting, and security investigations.

---

# Overview

SMTAP (Secure Multi-Tenant Audit Platform) is an enterprise backend application developed to securely collect, manage, verify, and investigate audit logs generated by modern software systems.

Unlike traditional logging solutions that simply store events, SMTAP focuses on **security**, **integrity**, **compliance**, and **investigation**. The platform ensures that audit records remain trustworthy through cryptographic verification while providing tenant isolation, role-based access control, and efficient search capabilities.

The system was designed using modern backend engineering principles with Spring Boot, PostgreSQL, Redis, JWT authentication, and Docker.

# Motivation

Modern organizations generate millions of audit events every day.

These events originate from:

- Authentication systems
- REST APIs
- Databases
- Internal services
- User activities
- Administrative operations

Traditional logging systems mainly focus on storing events. However, they often fail to address several important security requirements:

- Can someone modify historical logs?
- Can tenants securely share the same platform?
- Can investigators reconstruct an incident quickly?
- Can compliance reports be generated efficiently?
- Can suspicious activities be identified early?

SMTAP was designed to solve these problems.

# Authentication Flow

SMTAP uses JSON Web Tokens (JWT) for stateless authentication.

![Authentication Flow](/assets/images/smtap/auth-flow.png)

Authentication process:

1. User submits username and password.
2. Spring Security validates credentials.
3. JWT Access Token is generated.
4. Client stores the token.
5. Every request includes

```
Authorization: Bearer <JWT_TOKEN>
```

6. The backend validates the token before executing business logic.

Benefits:

- Stateless authentication
- High scalability
- Faster request processing
- Secure API communication

# Tamper-Evident Audit Logging

One of the primary objectives of SMTAP is to guarantee the integrity of audit records.

Traditional logging systems allow administrators or attackers with sufficient privileges to modify historical records. SMTAP prevents undetected modifications by linking every audit record using cryptographic hash chaining.

Every audit record stores:

- Current Hash
- Previous Hash

This creates an immutable sequence of audit events.

![Hash Chain](/assets/images/smtap/hash-chain.png)

```text
Log 1
Hash = H1

        │

Previous = H1

↓

Log 2
Hash = H2

        │

Previous = H2

↓

Log 3
Hash = H3

        │

Previous = H3

↓

Log 4
Hash = H4
```

If an attacker changes **any historical record**, every subsequent hash becomes invalid.

---

# Audit Verification Engine

SMTAP provides an integrity verification engine that validates the complete audit chain.

Verification process:

```text
Load Audit Records

↓

Recalculate Hash

↓

Compare Previous Hash

↓

Integrity Valid?

↓

YES → Verified

NO → Tampering Detected
```

Verification results include:

- Total Records Verified
- Verification Time
- Broken Hash Position
- Verification Status

This allows administrators to immediately detect unauthorized modifications.

---

# Why SHA-256?

SHA-256 was selected because it provides:

- Strong collision resistance
- Fast computation
- Industry adoption
- Fixed-length output
- Suitable for integrity verification

The platform uses SHA-256 exclusively for integrity validation rather than password storage.

# Engineering Decisions & Trade-offs

Building SMTAP required balancing security, maintainability, and performance. The following decisions reflect the trade-offs made during development.

## Why a Layered Architecture?

A layered architecture separates concerns into controllers, services, repositories, and security components.

### Advantages

- Clear separation of responsibilities
- Easier unit testing
- Better maintainability
- Simplified feature additions
- Reduced coupling between components

### Trade-off

Additional abstraction introduces slightly more boilerplate compared to a monolithic controller-based design, but significantly improves long-term maintainability.

---

## Why JWT Instead of Session-Based Authentication?

JWT enables stateless authentication, making the backend easier to scale horizontally.

### Advantages

- No server-side session storage
- Better suited for REST APIs
- Easier integration with frontend applications
- Supports distributed deployments

### Trade-off

Token revocation and refresh handling require additional implementation.

---

## Why PostgreSQL?

PostgreSQL was selected because of its strong ACID guarantees and mature support for relational data.

### Advantages

- Transaction support
- Reliable indexing
- Strong consistency
- Excellent Spring Boot integration

### Trade-off

Horizontal scaling is more complex than some NoSQL alternatives, but the relational model better fits audit and compliance data.

---

## Why Redis?

Redis is used to cache frequently accessed data such as dashboard statistics and authentication-related information.

### Advantages

- Low latency
- Reduced database load
- Faster response times

### Trade-off

Cached data introduces eventual consistency considerations and requires cache invalidation strategies.

---

## Why SHA-256 Hash Chaining?

Hash chaining provides tamper evidence for audit records without requiring a blockchain.

### Advantages

- Lightweight implementation
- Fast verification
- Detects unauthorized modifications
- Simple to integrate with relational storage

### Trade-off

Hash chains detect tampering but do not prevent deletion or replacement of the entire audit database. Additional protections such as immutable storage or external anchoring could strengthen guarantees.
